# PROJECT_OVERVIEW — CP Judge & Visual Tracer

> Generated by reading the actual source on disk (`main` branch, commit `cd0e733`). Every claim below references a real file/function.

## 1. What this project is

A web workbench for competitive programmers that **compiles and judges C++17 solutions** against built-in test cases, and **captures a real GDB-driven execution trace** (source line, locals, call stack at each step) that is replayed in a browser-based playback player. Problem data is hardcoded server-side; there is no database usage yet despite the Drizzle/Postgres scaffolding in `lib/db`.

**Execution/trace layer lives inside the API server**: `lib/cpp-runner.ts` compiles, runs, and traces user code exclusively inside the `cp-tracer-sandbox` Docker image (`docker/sandbox.Dockerfile`: non-root, g++, gdb) with `--network none`, 256MB memory (no swap), 1 CPU, and a pid cap. Docker is a hard requirement — both judge and trace fail loudly with 503 if the daemon is unavailable. On Replit, the path router maps `/api/*` → api-server (port 8080) and `/` → web (port 21424), per each package's `artifact.toml`.

## 4. How execution flows, end to end

### A. Judge submission (Run judge)

1. User clicks **Run judge** → `handleJudge()` in `artifacts/cp-judge-tracer/src/pages/home.tsx` calls the Orval mutation `useCreateSubmission().mutate({ data: { code, problemId } })`.
2. Request goes to `POST /api/submissions` → `artifacts/api-server/src/routes/judge.ts`. Body validated with `CreateSubmissionBody.parse(req.body)` (`{code, problemId}`, minLength 1).
3. Route looks up the problem in the in-memory array exported by `lib/problems.ts` (3 problems: `sum-two`, `reverse-array`, `fibonacci`), returns 404 JSON if missing.
4. For **each test case**, it calls `compileAndRun(code, test.input, 2200)` (`lib/cpp-runner.ts`):
   - Creates `mkdtemp("${tmpdir()}/cp-judge-*")`, writes `main.cpp`.
   - Compiles with `g++ -std=c++17 -g -O0 -fno-omit-frame-pointer ... -o main` (10 s compile timeout via `command()`).
   - Runs `main` with `runProcess()` (spawn, cwd=folder, sanitized env of just `PATH`, stdin fed the test input, SIGKILL at 2200 ms, stdout/stderr killed past 256 KB).
   - Folder removed in `finally` via `rm(folder, {recursive, force})`.
5. Per-test verdict computed in `routes/judge.ts`: outputs compared after trimming trailing whitespace per line + trailing newline (`normalize()`); per-test precedence is `TLE` (timedOut) → `RE` (exitCode ≠ 0) → `AC`/`WA`; overall aggregation at line 36 is `WA > TLE > RE > AC`. A compile error on any test short-circuits and returns the whole result with `verdict: "CE"` and compiler stderr in `compileError`.
6. Response is the `SubmissionResult` JSON (see §5), rendered by `ResultPanel` in `home.tsx`.

### B. Trace request (Visualize execution)

1. User optionally edits "trace stdin" textarea, clicks **Visualize execution** → `handleTrace()` in `home.tsx` calls `useCreateTrace().mutate({ data: { code, input } })` → `POST /api/trace` → `routes/trace.ts`.
2. `routes/trace.ts` validates with `CreateTraceBody.parse(req.body)` and calls `traceWithGdb(code, input)` (`lib/cpp-runner.ts`).
3. `traceWithGdb` (maxSteps default 2000):
   - `compileOnly()` writes sources to a temp dir and compiles with debug symbols (`-g -O0 -fno-omit-frame-pointer`). Compile failure → immediate return `{trace: [], error: <compiler stderr>, truncated: false}`.
   - Writes user input to `stdin.txt`, then spawns `gdb --interpreter=mi2 ./main` and drives it over stdio with MI commands: `-gdb-set pagination off`, `-gdb-set confirm off`, `set step-mode off`, `-break-insert main`, then `-interpreter-exec console "run < ${inputPath}"` (console redirection chosen deliberately because tty redirection makes stdin behave like EOF — see `.agents/memory/gdb-tracing.md`).
   - A hand-written MI parser (`miField`, `miObjects`, `miFrames`, `miVariables` — regex + balanced-brace scan, lines 121–180) handles `*stopped` records and command results.
   - Per stop, a small state machine runs: read top frame → `-stack-list-frames` (full stack) → `-stack-list-variables --simple-values` (locals) → push one trace step → `-exec-step`. Source-less library stops (`reason="end-stepping-range"` without frames) are re-stepped, not fabricated. Program exit ends capture; global hard timeout is 10 s (`truncated: true`); reaching `maxSteps` sends `-gdb-exit`.
   - All raw MI output is also appended to `gdb-mi.log` in the temp folder (deleted on cleanup).
4. Response is `TraceResult` (`{trace, source, truncated, error}`). No synthetic fallback trace exists by design — failures surface as `error` text (per `.agents/memory/gdb-tracing.md`: *"surface any other GDB stop failure instead of synthesizing a trace"*). This tracer path is real GDB data, not a simulation.
5. Frontend: `handleTrace` stores the whole result in `sessionStorage["cp-trace-result"]` and navigates to `/trace` (`home.tsx:210-211`).
6. `pages/trace.tsx` reads `sessionStorage` once on mount and renders: `StepRail` (timeline buttons), `SourcePanel` (active-line highlighting), `LocalsPanel` (highlights values changed vs previous step), `StackPanel` (call-stack frames), `ArraysPanel` (array cells). Controls: prev/next step, play/pause (850 ms interval, `trace.tsx:117-127`), reset.

## 5. Data models / API contracts

All paths mounted under `/api` (`app.ts`). Schemas defined in `lib/api-spec/openapi.yaml`, generated as Zod/TS in `lib/api-zod/src/generated/types/` and as TS interfaces in `lib/api-client-react/src/generated/api.schemas.ts`. Field names below are exact.

### Endpoints

| Method & Path | Handler | Request | Response |
|---|---|---|---|
| `GET /api/healthz` | `routes/health.ts` | — | `{ status: string }` (`"ok"`) |
| `GET /api/problems` | `routes/problems.ts` | — | `Problem[]` |
| `GET /api/problems/:problemId` | `routes/problems.ts` | path param validated by `GetProblemParams` | `Problem` or `404 {error: "Problem not found"}` |
| `POST /api/submissions` | `routes/judge.ts` | `SubmissionInput` | `SubmissionResult` |
| `POST /api/trace` | `routes/trace.ts` | `TraceInput` | `TraceResult` |

### Shapes

```yaml
Problem:            { id, title, difficulty, description, starterCode: string,
                      testCases: [{ id, input, expectedOutput }] }
SubmissionInput:    { code: string(minLength 1), problemId: string }
TestCaseResult:     { id, verdict, actualOutput, expectedOutput: string,
                      runtimeMs: number, error: string|null }
SubmissionResult:   { verdict, totalRuntimeMs: number,
                      tests: TestCaseResult[], compileError: string|null }
TraceInput:         { code: string(minLength 1), input: string }   # input required in schema
TraceLocal:         { name, type, value: string }
TraceFrame:         { function: string, line: number }
TraceArray:         { name, type: string, values: string[] }
TraceStep:          { step: number, line: number, function: string,
                      locals: TraceLocal[], stack: TraceFrame[], arrays: TraceArray[] }
TraceResult:        { trace: TraceStep[], source: string,
                      truncated: boolean, error: string|null }
```

Verdict values observed in code: overall `CE | WA | TLE | RE | AC`; per-test `TLE | RE | AC | WA` (`routes/judge.ts:29,36`).

### Persistence

None. There are **no SQL tables** — `lib/db/src/schema/index.ts` contains only comments and `export {}`. Problems live in the in-memory fixture array; submissions/traces exist only in HTTP responses (the last trace is kept client-side in `sessionStorage`, nothing survives a new tab).

## 7. Known issues

1. **No sandbox isolation (security)**: compiled user code executes directly with full process privileges. Only mitigations are time and output-size caps (`cpp-runner.ts:16-49`). A malicious submission can read/write the host filesystem, open sockets, fork-bomb (within output caps), etc.
2. **No memory or CPU limits**: a program allocating gigabytes is stopped only by wall-clock timeout; OOM degrades unpredictably.
3. **Request-body validation fails into raw 500s**: routes call `.parse()` (e.g., `routes/judge.ts:9`), so invalid bodies throw `ZodError`. There is no Express error-handling middleware (`src/middlewares/` contains only `.gitkeep`); runner/GDB IO errors also surface as generic 500s (Express 5 catches rejected async handlers).
4. **Compile happens N times per judged submission**: `compileAndRun` runs inside the test-case loop (`judge.ts:14-15`) — 3 test cases means 3 identical g++ invocations.
5. **Per-test timing is misleading**: `runtimeMs` starts before compilation (`cpp-runner.ts:82,97`), inflating every test by compile time.
6. **Hardcoded limits everywhere**: 2200 ms judge timeout (`judge.ts:15`), 2000-step / 10 s trace caps (`traceWithGdb` signature and timer, `cpp-runner.ts:182,222`) — none configurable per problem or via env.
7. **GDB command/response pairing is fragile**: the loop uses a single-slot `pending` state variable and ignores its own issued tokens (`send()` sets pending before writing the `token++` command; responses are matched by order only, `cpp-runner.ts:207-280`). Interleaved records could mis-pair steps on long traces.
8. **Locals content is lossy**: `--simple-values` cannot expand structs/vectors — such variables arrive as GDB summary text (e.g. `{...}`) — and an aggregate named exactly `main` or `fib` would be silently dropped (`cpp-runner.ts:179`).
9. **Frontend cannot reach the API when self-hosted**: Orval generates relative `/api` URLs, `setBaseUrl()` (exported in `lib/api-client-react/src/custom-fetch.ts`) is never called anywhere in app code, and `vite.config.ts` has **no dev proxy**. Calls only succeed because Replit's path router forwards `/api/*` to the API service (per each package's `.replit-artifact/artifact.toml`). Running the web dev server locally yields `/api` requests hitting Vite itself (404).
10. **Wide-open CORS + no rate limiting/auth** (`app.use(cors())`, `app.ts:28`): each judge/trace request triggers compiler/GDB processes on the shared host.
11. **Verdict aggregation hides mixed results**: WA > TLE > RE precedence (`judge.ts:36`); one WA displays "WA" even if other tests TLE'd or RE'd — defensible, but undocumented.
12. **Trace payloads round-trip through sessionStorage** (`home.tsx:210`): large traces risk browser quota (~5 MB typical); nothing survives opening a new tab.

## 8. How to run it locally

Prerequisites: **Node.js 24+, pnpm, g++ (C++17 capable), gdb**. (`gdb` comes from `.replit` nix packages; outside Replit install it yourself.) There is no Docker/compose setup and no `.env.example`.

```bash
# 1. Install (root preinstall hook enforces pnpm)
pnpm install

# 2. Regenerate clients if you change lib/api-spec/openapi.yaml
pnpm --filter @workspace/api-spec run codegen

# 3. Start the API server (esbuild bundle + start; needs PORT)
PORT=8080 pnpm --filter @workspace/api-server run dev      # serves /api/*

# 4. In another terminal, start the web app (needs PORT and BASE_PATH)
PORT=21424 BASE_PATH=/ pnpm --filter @workspace/cp-judge-tracer run dev   # Vite on :21424
```

Required environment variables (both enforced with hard startup errors): `PORT` (`api-server/src/index.ts:6` and `cp-judge-tracer/vite.config.ts:10`), `BASE_PATH` (vite config, used as Vite `base`). `DATABASE_URL` is *not* needed unless you start importing `@workspace/db`.

⚠️ Because of issue #9 above, local browsing fails to reach `/api` out of the box unless both processes share an origin (e.g. reverse-proxy `/api → localhost:8080` in front of Vite) or you temporarily wire `setBaseUrl("http://localhost:8080")` before queries run. Under Replit's "Project" workflow button, routing happens automatically.

Other useful commands (root `package.json` / `replit.md`):

```bash
pnpm run typecheck        # tsc across all workspace packages
pnpm run build            # typecheck + build everything
```

## Recommended Improvements

### Critical

1. ~~**User-submitted binaries run unsandboxed.**~~ **DONE** — all compilation, judging, and GDB tracing now run inside the `cp-tracer-sandbox` image (non-root uid/gid mapped from host, `--network none`, read-only except `/work`, Docker required or endpoints fail loudly).
2. ~~**Add an Express error middleware / rate limiting on heavy endpoints.**~~ **DONE** — `src/middlewares/error-handler.ts` maps ZodError/malformed bodies to structured 400s and docker outages to 503; `src/middlewares/job-queue.ts` gates `POST /submissions` and `POST /trace` behind a semaphore (`MAX_CONCURRENT_JOBS=2`, queue depth `MAX_QUEUE_DEPTH=8`, overflow → 429). CORS is origin-allowlisted via `ALLOWED_ORIGINS` (local dev origins auto-allowed outside production); request bodies capped at 256KB.
3. ~~**Enforce memory + CPU limits alongside time limits.**~~ **DONE** — enforced at the container level in `cpp-runner.ts`'s `dockerRunArgs()` (`--memory/--memory-swap 256m`, `--cpus 1`, `--pids-limit 128`) plus wall-clock timeouts, verified via live `docker inspect`.

### Important (needed for the app to be genuinely useful)

1. ~~**Populate the data-structure view with real data.**~~ **DONE** — per-step `arrays` now carries live contents for C arrays, `std::vector`, and `std::array` (the whole `ArraysPanel` UI consumes it). Extraction is deliberately python-free: vector layout arithmetic on `_M_impl._M_start/_M_finish`, expression-based `_M_elems` reads for `std::array` — because libstdc++ Python pretty-printers hang GDB forever on half-initialized containers (see `.agents/memory/gdb-tracing.md`). Raw pointers into arrays remain out of scope (no reliable length).
2. ~~**Expand locals beyond simple values / remove filter hack.**~~ **DONE** — value-less (`--simple-values`) aggregate locals are expanded: struct/class members flatten one level as dotted rows (`p.x`), strings keep readable content, sequences become array views; the old `main/fib` name filter is gone. **Bonus fixes in the same pass:** MI responses are matched by command token (fixes fragility #5); STL-internal stops are skipped via `-exec-finish` so traces show only user-code steps; expansion commands run under a 750ms watchdog; failed traces preserve their folder + `gdb-mi.log` for post-mortem debugging.
3. ~~**Compile once per submission.**~~ **DONE** — `compileSubmission()` (`cpp-runner.ts`) compiles once into a sandbox temp folder (owner of the compile in the failure path), returning `{ok, program}` or `{ok:false, compileError}`; `runProgram()` runs the same binary per test, so `runtimeMs` measures only the run phase. `routes/judge.ts` calls `compileSubmission` once and loops `runProgram` across test cases, cleaning up in `finally`; `compileAndRun` remains as a thin single-shot wrapper. Verified: sum-two's 3 tests each ~350–450 ms with no compile folded in (total 1177 ms), all AC; CE returns the container-path g++ stderr with `tests:[]`; trace unchanged.
4. ~~**Make limits configurable.**~~ **DONE** — the four fixed time constants are now env-driven with defaults in `cpp-runner.ts`: `RUN_TIME_LIMIT_MS` (2200), `COMPILE_TIMEOUT_MS` (10000), `TRACE_MAX_STEPS` (2000), `GDB_HARD_TIMEOUT_MS` (10000). Judge, compile, and trace all read the configured values; additionally, per-problem `time_limit_ms` is honored from the DB. Verified both dimensions live: DB row `time_limit_ms=1` → all tests TLE, `2200` → AC; no-DB fallback with `RUN_TIME_LIMIT_MS=1` → TLE.
5. ~~**Harden MI pairing**: match incoming `N^done` records against their issued token instead of the single-slot `pending` flag (`cpp-runner.ts:207-225`) so long traces can't mis-attribute responses.~~ **DONE** — the driver now dispatches results through a token-keyed resolver map.
6. ~~**Fix frontend→API wiring for non-Replit hosting**.~~ **DONE** — the Vite dev/preview proxy for `/api/*` was already present in `vite.config.ts` (points to `API_ORIGIN`/`VITE_API_ORIGIN`, default `localhost:8080`). Wired it up by calling `setBaseUrl(import.meta.env.VITE_API_URL || null)` in `main.tsx` so production builds (no proxy) target the correct API origin; when unset, requests stay relative and the dev proxy handles `/api/*`. For cross-origin production deployments the API's existing `ALLOWED_ORIGINS` allowlist must include the frontend origin (set it when serving the built frontend from a different origin than the API). Verified live: production build baked `VITE_API_URL=http://localhost:8099`; served it via `vite preview` on `:5174`, confirmed CORS returns `Access-Control-Allow-Origin: http://localhost:5174` and `/api/problems` 200s; dev proxy at `:5173` also proxies `/api/*` to `:8099` correctly.
7. ~~**Persist problems via `@workspace/db` or drop it.**~~ **DONE** — a `problems` table now exists in `lib/db/src/schema/index.ts` (`id`, title, difficulty, description, starterCode, `test_cases` jsonb, plus per-problem `time_limit_ms`/`compile_timeout_ms`/`max_trace_steps`). The DB is **optional**: `lib/problem-repo.ts` lazy-loads `@workspace/db` only when `DATABASE_URL` is set and falls back to the in-memory fixtures otherwise; judge/problem routes read through it. `pnpm --filter @workspace/api-server run db:seed` seeds the three built-ins idempotently. Public Problem responses keep the exact OpenAPI shape (limits stripped). Verified live against a real Postgres: DB reads flow to judge (limit toggle flips AC↔TLE), 0 fallback warnings, seed idempotent.
8. **Cache/share traces server-side**: store `TraceResult` under an ID and hand back a URL instead of round-tripping megabytes through `sessionStorage` (`home.tsx:210`), which also risks browser quota.
